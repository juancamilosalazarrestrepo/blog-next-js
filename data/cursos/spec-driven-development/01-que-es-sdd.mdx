## El problema de escribir código directamente

Cuando abres tu editor y empiezas a escribir código sin un plan, algo inevitable pasa: a los
20 minutos te encuentras reescribiendo lo que hiciste hace 5, refactorizando estructura que
deberías haber pensado antes, o descubriendo que tu "solución rápida" no escala para nada.

Esto no es un problema tuyo. Es el problema de **programar sin especificar**.

<Callout type="nota">
  Spec-Driven Development (SDD) no es una moda ni un framework. Es una disciplina simple:
  <strong>primero defines QUÉ construir y CÓMO se relaciona todo, y solo después dejas que la
  IA (o cualquier herramienta) escriba el código.</strong>
</Callout>

## Qué es una especificación

Una especificación (o "spec") es un documento que describe **qué debe hacer** un sistema sin
importar cómo se escribe internamente. Piensa en ella como los planos de un arquitecto antes
de construir una casa: no dicen qué marca de ladrillo usar, sino dónde van las paredes, las
puertas y las ventanas.

Una buena spec para un proyecto de software incluye:

- **Contexto**: para qué sirve el proyecto, quién lo usa.
- **Objetivos**: qué debe lograr concretamente.
- **Arquitectura**: cómo se divide el sistema en partes y cómo se relacionan.
- **Stack tecnológico**: qué herramientas se usan y por qué.
- **Alcance**: qué SÍ está incluido y qué NO.
- **Restricciones**: límites técnicos, de diseño o de tiempo.

## El ciclo SDD en tres pasos

Todo el método se reduce a esto:

1. **Especificar**: escribes (o generas con IA) un documento que define el proyecto completo.
2. **Planificar**: divides la spec en tareas individuales, ordenadas y verificables.
3. **Implementar**: le das cada tarea a una herramienta de IA (Claude Code, OpenCode,
   Antigravity, etc.) que genera el código respetando la spec.

<Callout type="tip">
  La magia de SDD es que la IA produce código <strong>mucho mejor</strong> cuando le das una
  spec clara que cuando le dices "hazme una app de tareas". La calidad de la entrada
  (tu especificación) determina la calidad de la salida (el código).
</Callout>

## SDD vs. el método tradicional con IA

| Método tradicional con IA | Spec-Driven Development |
|---|---|
| "Hazme una app de tareas con React" | Spec de 2 páginas → 8 tareas → código |
| La IA adivina la arquitectura | Tú defines la arquitectura en la spec |
| Refactorización constante | Cambios puntuales en la spec |
| No sabes qué pedir cuando algo falla | Cada tarea tiene un criterio de verificación |
| El proyecto crece sin control | El alcance está definido desde el inicio |

## Por qué esto importa ahora más que nunca

En 2026, los agentes de IA como Claude Code y OpenCode pueden ejecutar tareas de 5 a 15
pasos de forma autónoma. Pero "autónomo" no significa "sin dirección". Un agente sin una
spec es como un constructor sin planos: puede hacer cosas impresionantes, pero probablemente
no las que tú necesitas.

SDD te da el control de dirección mientras la IA se encarga de la ejecución.

## Para recordar

- Una especificación define QUÉ construir, no CÓMO se escribe el código.
- El ciclo SDD es: Especificar → Planificar → Implementar.
- La calidad de tu spec determina la calidad del código que genera la IA.
- SDD no reemplaza tu criterio: lo amplifica.
